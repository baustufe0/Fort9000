# CLAUDE.md – FORT 9000

Mod for the game **Forts** (Steam) that extends the built-in AI, records matches and retrains its parameters.
Specification: [.dev/SPEC.md](../.dev/SPEC.md) is a short index of `.dev/docs/` (topic files, `.dev/docs/maps/<map>.md` for the current
state of each map's plans, `.dev/docs/history/` for test matches). Read the index, then only the files the task needs.

This folder is both the git repo and the installed mod:
`<Steam>/steamapps/common/Forts/data/mods/fort-9000` (Windows). The Forts install is three levels up.

## Language

Write **everything in English**: code, comments, log messages, docs, commit messages, test output.
Only exception: the German entry in `displayname.lua` (in-game localisation).

## Layout

The root holds only what the game loads and the Workshop upload ships (`ai/`, `fortplans/`, `mod.lua`, `displayname.lua`,
`script.lua`, `preview.jpg`, `LICENSE`). Everything for development lives in dot folders, which the upload skips:
`.dev/` (tools, docs, SPEC), `.claude/` (this file, skills), `.github/` (README).

- `script.lua` – recorder (writes `[CREC]` lines to the Forts log, read-only)
- `ai/ai.lua` – AI extension; runs AFTER the built-in `data/ai/ai.lua` and wraps its functions
- `ai/strategy.lua` – trained parameters, **generated by `.dev/tools/train.py`; do not edit by hand**
- `ai/fortplans.lua` – maps, plan lists, per-map strategy overrides (never touched by training)
- `fortplans/<Map>/` – custom build plans (`fort-*.lua`)
- `.dev/tools/train.py`, `.dev/tools/train.bat` – collect logs + train
- `.dev/tools/fortgen/` – plan generator and helpers (needs Pillow for rendering)
- `.dev/tools/tests/` – Lua tests (`run_tests.sh`)
- `.dev/tools/logs/`, `.dev/tools/_alt/`, `last_training.json` – local only (git-ignored)

## Commands

- Train: `python .dev/tools/train.py` (or `.dev\tools\train.bat`); `report` shows evaluation without writing.
- Tests: `bash .dev/tools/tests/run_tests.sh <lua5.1-binary> <Forts>/data`
  (needs Lua 5.1; see the header of `run_tests.sh`; `LuaPlusC.exe` in the Forts folder may also work, untested).
  The plan-swap tests need the game's `data/maps` and `data/ai` folders.
- Generate plans: see the docstring of `.dev/tools/fortgen/gen_fort.py`; check them with `rules.py` (fort building rules,
  `.dev/docs/building-rules.md` – read it before changing plans or the generator; for one map also `.dev/docs/maps/<map>.md`) and `render_all.py`.
- Physics check of plans (sag, strut stress, struts refused in build order, collapse): `python .dev/tools/fortgen/physics.py check fortplans/Vanilla/*.lua [--png out.png]`
  (`.dev/docs/physics.md`; the starting fort comes from the map's `.spr`: `.dev/tools/fortgen/spr.py`, `.dev/docs/map-files.md`).
- Plan from a player's build: build the fort (sandbox, no combat), then
  `python .dev/tools/fortgen/rec_fort.py --map Vanilla --out fortplans/Vanilla/fort-t1f1-Vanilla-<n>.lua` (`.dev/docs/recorder-training.md`).
- Map where the game refuses devices (`CS_UNSTABLE`): set `Probe` in `ai/fortplans.lua`, let the plan build in a sandbox,
  then `python .dev/tools/fortgen/probe.py [--csv out.csv] [--png out.png]` (`.dev/docs/debugging.md`). Never commit `Probe` switched on.
- The Forts log is `<Forts>/users/<steam-id>/log.txt`; it is overwritten on every game start.
  Run `train.py collect` after each play session.

## Rules that must not be broken

- **Deterministic only.** No wall-clock time, no `math.random`. Randomness only via `GetRandomInteger`.
  Otherwise replays and multiplayer desync.
- **Wrap, don't replace.** Save the original function (`local CAI_BaseX = X`), call it, then add logic.
- **`pcall` around all custom logic.** An error must never abort a match; log it as `[CAI] ERROR ...`.
- **`dofile` only during initialisation.** `rawget`/`rawset` do not exist in Forts Lua.
- **No bitwise operators (`|`, `&`, `~`, `<<`) in the mod's Lua files.** The game's Lua accepts them (the built-in
  AI uses `FIREFLAG_A | FIREFLAG_B`), but the tests run Lua 5.1, where the file then does not load at all. Flags
  are separate bits, so add them (`RAY_A + RAY_B`).
- **Forts removes foreign files from `data/maps`**, so custom plans stay in `fortplans/`.
- **Plan files are line-sensitive** (the game's AI relies on line numbers); keep the generated header intact
  and write them with CRLF as `gen_fort.py` does.
- `strategy.lua` is written as ASCII by `train.py`.

## Log format contract (parsed by `train.py`)

Do not change these without updating `train.py` and the tests:
- `[CREC] f=<frame> START|SNAP|BUILT|LOST|RESULT ...` (recorder lines; `START ... restart=1` after a restart)
- `[CREC] f=<frame> NODE|LINK|DEV|GDEV|UNNODE|UNLINK|DEL ...` (build events, parsed by `.dev/tools/fortgen/rec_fort.py`)
- `[CAI] T<team> PLAN map=<map> file=<plan> ...`
- `[CAI] T<team> END winner=<n> ...`
- `ActivateAI team <n> team members <m> fort <file>` (written by the game itself)

`[CAI] T<team> PROBE START|NODE|LINK|TRY|LOAD|WAIT|END ...` are parsed by `.dev/tools/fortgen/probe.py` (and make `train.py` skip the match).

Other `[CAI]` messages (`THINK`, `GAVE_UP`, `SKIPPED`, `MODULES`, `MODULE`, `MODULE_WAIT`, `REBUILD_CAP`, `FLAK_HOLD`, `SMOKE_WAIT`, `RETIRE`, `RETIRE-CONFIG`, `BUILD_ERROR`, `SHAPE`, `STRESS`, `FIRE`, `FIREWAIT`, `FIRETRY`, `VOLLEY`, `VOLLEY_HOLD`, `VOLLEY_TIMEOUT`, `TEMPO`, ...) are used by the
tests in `.dev/tools/tests/run_tests.sh`; keep them in sync when renaming.

## Workflow

1. Make the change; keep it small and focused.
2. Run the tests (see above) and, for AI changes, play or replay a match and check the `[CAI]` lines in the log.
3. If behaviour changed, update the docs in the same commit: the topic file in `.dev/docs/` and, for a plan, its map file
   in `.dev/docs/maps/`. A test match goes into `.dev/docs/history/<plan>.md`; add a new file to the index in `.dev/SPEC.md`.
4. Commit with a short imperative message in English; `git push` to `origin main`.

## Notes

- Old archived logs in `.dev/tools/logs/` contain German `[CAI]` tokens from before the translation; `train.py`
  does not parse them, so they remain usable.
- Project skills in `.claude/skills/`: `forts-match-review` (analyse a played match, archive the log, train;
  `summary.py` summarises a log) and `forts-map-plans` (change, generate and install build plans, per-map settings).
  They hold only the workflow and point to `.dev/docs/`; keep facts in `.dev/docs/`, not in the skills.
